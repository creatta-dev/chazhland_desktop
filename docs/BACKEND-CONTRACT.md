# Контракт с бэкендом

Каталога REST-путей здесь нет — и не будет. Рукописный список эндпоинтов протухает за пару спринтов
(прошлая версия этой страницы отстала от кода на пять доменов), а живой контракт бэк отдаёт сам.
Документ описывает то, чего в спеке не прочитать: **как устроен клиентский слой доступа к API** и
**что в контракте неочевидно**.

## 1. Где смотреть актуальный контракт

| Вопрос | Источник истины |
|---|---|
| Какие есть пути, параметры, коды ответов, схемы | **Swagger UI бэка:** `<API_BASE>/swagger-ui.html`, машинная спека — `<API_BASE>/v3/api-docs`. Springdoc генерит её из контроллеров (`packages-to-scan: com.chazhland.messenger`), поэтому она не отстаёт от кода. Оба пути открыты без авторизации; на бэке гасятся через `SPRINGDOC_ENABLED=false`. |
| Точные поля, nullability, бизнес-правила | **Java-код бэка** (репозиторий `chazhland-back`): контроллеры `com.chazhland.messenger.web` и DTO `…web.dto`. Спека показывает форму ответа, но не условия — «когда 403», «что значит `null`». |
| Что из этого реально дёргает десктоп | **`src/lib/api.ts`** — единственный файл клиента, где встречаются пути бэка. Grep по нему честнее любой таблицы в доке. |
| Какими типами оперирует UI | `src/lib/types.ts` (типы UI) плюс локальные `…Dto`-интерфейсы в шапке `api.ts` (сырые ответы бэка). |
| Realtime | **`src/lib/ws.ts`** — STOMP-топиков в OpenAPI нет вообще, другого источника истины не существует. |

> Локальный бэк: `http://localhost:8080/swagger-ui.html`. Прод: `https://api.chazhland.ru/swagger-ui.html`.

## 2. Куда ходит клиент

| Назначение | Прод-адрес | Откуда клиент его берёт |
|---|---|---|
| REST API | `https://api.chazhland.ru` | `VITE_API_BASE` |
| STOMP-over-WebSocket | `wss://api.chazhland.ru/ws` | `VITE_WS_URL` (по умолчанию выводится из `VITE_API_BASE`) |
| LiveKit (голос, демонстрация экрана) | `livekit.chazhland.ru` | из ответа `POST /livekit/token` (поле `url`), **не** из env |
| Файлы (MinIO, S3-совместимое) | `https://s3.chazhland.ru` | presigned-URL и `url` вложений отдаёт бэк; клиент адреса не конструирует |

Переменные окружения и mock-режим — в [README §6](../README.md#6-конфигурация) и
[BUILD.md §3](./BUILD.md#3-dev-режим).

### Подмена заголовка Origin (только Electron)

Бэк проверяет `Origin` при WS-handshake, а в паковой сборке рендерер грузится из `file://` → handshake
отбивался 403 и клиент вечно переподключался. Поэтому `electron/main.ts` в хуке `onBeforeSendHeaders`
подменяет `Origin: https://chat.chazhland.ru` для запросов на хост `api.chazhland.ru` по схемам
`https:` / `wss:` (только TLS: cleartext-запрос не должен нести доверенный Origin). Фильтр именно по
hostname — match-pattern со схемой `wss://` в Electron WebSocket-handshake не матчит, на этом уже
обжигались.

## 3. Как устроен слой доступа

```
features/*  ──▶  lib/api.ts  ──▶  lib/http.ts  ──▶  fetch(API_BASE + path)
                     │                └ Bearer, refresh по 401, разбор ошибок
                     └─(MOCK)─▶ mocks/data.ts
lib/ws.ts   ──▶  STOMP (подписки и публикации, JWT в кадре CONNECT)
```

- **`config.ts`** — три переменные (`VITE_API_BASE`, `VITE_WS_URL`, `VITE_MOCK`), другой конфигурации у
  клиента нет. `MOCK` включается строго строкой `'true'`: отсутствие переменной или опечатка = живой
  бэк (однажды прод-сборка молча ушла в моки — с тех пор проверка строгая).
- **`http.ts`** — один дженерик `http<T>(path, opts)`: подставляет `API_BASE`,
  `Content-Type: application/json` и `Authorization: Bearer`, на `401` делает single-flight
  `/auth/refresh` и **один** повтор запроса, `204` отдаёт как `undefined`, любой не-2xx превращает в
  `HttpError(status, body)`.
- **`api.ts`** — прикладные методы. Здесь же локальные `…Dto` (форма ответов бэка), мапперы
  `mapMessage` / `mapMember` / `mapChannel` в UI-типы (компоненты сырых DTO не видят), кэш `memberMap`
  для резолва авторов сообщений и аудита (ленивая подгрузка `members()` перед маппингом),
  presign-загрузка файлов и `mapIncoming` — тот же маппер для сообщений, прилетевших по WS.
- **Mock-ветка в методе.** Тело почти каждого метода начинается с `if (MOCK) { … }`. Добавляете метод —
  добавьте и мок, иначе разработка UI без бэкенда ломается ровно на вашем экране.
- **Серверные и «домашние» роуты.** Клиент мульти-серверный: большинство методов принимают
  необязательный `serverId` и выбирают либо `/servers/{serverId}/…`, либо легаси-роут домашнего сервера
  (`/server/tree`, `/server/members`, `/roles`, `/members/{id}`). Операции над сущностью по её id
  (`/channels/{id}`, `/roles/{id}`) серверного префикса не имеют — бэк выводит сервер из самой сущности.
- **Текст ошибки для тоста** — `apiError(e, fallback)` из `http.ts`: берёт первую ошибку поля из
  `fieldErrors` (у валидации `message` = «Validation failed», толку ноль), иначе `message` тела
  `ApiError`, иначе fallback. Не сочиняйте свои формулировки поверх серверных.

## 4. Аутентификация

- Схема **Bearer**: access-токен живёт **только в памяти**, refresh — в `localStorage` под ключом
  `chazh.refresh`.
- Refresh **одноразовый и ротируется**: `/auth/refresh` гасит предъявленный токен и выдаёт новую пару.
  Предъявление уже погашенного = reuse-detection: бэк отзывает **все** сессии пользователя.
- Отсюда single-flight в `http.ts`: параллельные `401` ждут один общий вызов `/auth/refresh`. Иначе
  гонка убила бы сессию собственным reuse-detection'ом.
- Исход ротации различает три случая: `ok` → повтор исходного запроса; `auth-failed` (сервер отверг
  токен) → чистим сессию, рвём WS, экран входа; `network-error` → отдаём ошибку наверх, **сессию не
  трогаем** (иначе моргнувший Wi-Fi разлогинивал бы).

## 5. Realtime (STOMP)

Клиент — [`src/lib/ws.ts`](../src/lib/ws.ts); в mock-режиме весь класс — no-op.

- Подключение по `VITE_WS_URL`, JWT (тот же access-токен, что и в REST) передаётся заголовком кадра
  `CONNECT`. Heartbeat 10 с, задержка переподключения 3 с, логические подписки переживают реконнект.
- После ротации access-токена WS переподключается с новым токеном (колбэк `setOnTokenRefresh`).
- Подписки (server → client): `/topic/channel.{channelId}` (сообщения, реакции, набор текста),
  `/topic/watch.{channelId}` (полный `WatchState` на каждое изменение), `/topic/presence`
  (легаси-общий) и серверные `/topic/server.{serverId}.{presence|rank|quorum|achievement|afk}`.
- Публикации (client → server): `/app/channel.{channelId}.typing`, `/app/watch.{channelId}.control`,
  `/app/presence.heartbeat`.
- Точный список — в `ws.ts`. В OpenAPI STOMP не попадает, но и дублировать его здесь смысла нет: все
  топики объявлены в одном файле, рядом с комментариями.

## 6. Неочевидное в контракте

| Тема | Что нужно знать |
|---|---|
| **Идемпотентность отправки** | `POST /channels/{id}/messages` несёт `clientMessageId` (UUID, генерится в `api.sendMessage`). Бэк дедуплицирует по паре «автор + clientMessageId» и на повтор возвращает уже сохранённое сообщение вместо второго. Поэтому автоповтор после refresh безопасен. Новый вызов `sendMessage` = новый nonce: повторная отправка руками дубль всё-таки создаст. |
| **Курсорная пагинация** | `?before={id}` — старше курсора, `?after={id}` — новее, `limit` (по умолчанию 50, потолок 100). Курсор **исключает** опорное сообщение: при переходе из поиска/пинов саму цель домерживаем отдельно (`api.contextMessages`). Порядок ответа разный: без курсора и с `before` — newest-first, с `after` — oldest-first. Клиент на порядок не полагается и пересортировывает по id. |
| **Конверт `Page<T>`** | `{ items, nextCursor, hasMore }` — у эндпоинтов с потенциально длинным списком (история канала, поиск, `changes`, аудит). Заведомо ограниченные списки (дерево каналов, участники, роли, пины, DM) отдаются **голым массивом**: по форме ответа фронт и отличает «страницу» от «всего набора». Угадывать нельзя — смотрите схему в swagger. |
| **ULID вместо инкремента** | Id сообщений — ULID: лексикографический порядок = хронологический. Сортировка по одному только id и есть сортировка по времени. |
| **Presign-загрузка** | Три фазы: (1) `POST /attachments/presign` `{filename, contentType, size}` → `{uploadUrl, objectKey}`; (2) прямой `PUT` файла по `uploadUrl` **без заголовка `Authorization`** — URL уже подписан, бэк в этом шаге не участвует; (3) `objectKey` уходит в массиве `attachments` при отправке сообщения, и только тогда бэк проверяет объект `statObject`'ом (фактические тип/размер и владелец presign'а — чужой объект привязать нельзя). Ссылка живёт ~10 минут, `contentType` сверяется с белым списком уже на шаге 1: файл с нераспознанным MIME (клиентский фолбэк `application/octet-stream`) получит 400 сразу на presign. |
| **Превью вложений** | `thumbnailUrl` бэк проставляет асинхронно, уже после ответа, и только для JPEG/PNG — в только что отправленном сообщении он `null`. Клиент его не использует вовсе: превью строится из `url` + `width`/`height`, а размеры замеряются на клиенте до загрузки, чтобы лента не прыгала. |
| **`204` — это не ошибка** | `http()` отдаёт `204` как `undefined`. Пример: `GET /channels/{id}/watch` возвращает 204, когда источник просмотра не задан, и `api.watchState` превращает это в `null`. |
| **Тело ошибки** | `ApiError { status, message, timestamp, fieldErrors? }`; `fieldErrors` есть только у `400` от `@Valid`. Разбор — `apiError()`, см. [§3](#3-как-устроен-слой-доступа). |
| **Токен LiveKit** | `POST /livekit/token` `{channelId}` → `{ token, url, room }`. Адрес комнаты берётся из `url` ответа: в env клиента LiveKit не прописан. |

## 7. Что делать при расхождении

1. Открыть swagger бэка и сверить путь/схему — спека генерится из контроллеров и врёт реже документации.
2. Вопрос про поведение (когда 403, что значит `null`, есть ли дедупликация) — читать Java-код:
   контроллер → сервис.
3. Правку вносить в `src/lib/api.ts` (и в мок рядом). В этот документ — только если появилась новая
   **неочевидность**. Перечень путей сюда не возвращать.
